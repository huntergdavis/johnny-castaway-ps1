BSOD — A Fatal Error Screen for PS1

Editor's note. The PS1 port now drops into a Windows-3.1-style blue screen when a scene's setup runs out of heap or asset data. The screen is loud on purpose: it should never fire in production, and when it does it's the only thing on a deterministic test build that prevents a silent visual fail.

The screensaver is a long-running loop. Every iteration tears down the previous scene's per-scene allocations — the streaming frame buffer, the rect-mode clean-bg snapshot, the variant-overlay BMP slots — and stands up new ones for whatever scene came up next. On a 2 MB PS1 with no swap and a malloc that prefers contiguous chunks, "stand up new ones" is the operation that fails first when something is wrong.

What happens when it fails is that the scene-setup code path returns early. The previous scene is gone, the new one never came up. Nothing plays, the screen freezes on whatever the last frame was, and there's no signal in the visual to tell you which call returned the unhappy path.

That is exactly the failure mode you can't ship. It's also exactly the failure mode you can't easily debug from a captured TTY log alone, because by the time TTY catches up, you've usually moved on to debugging something else and the failure has already been memory-holed by the next scene's successful setup.

What the BSOD shows

When a scene's setup hits a fatal error path, the runtime now calls JC_BSOD(scene, reason). That macro hands off to ps1Bsod() in src/ps1_debug.c, which:

  • resets the GPU to standard 320 × 240 NTSC,
  • fills the framebuffer with Win 3.1 BSOD blue (RGB(0, 0, 168)),
  • opens a BIOS 8 × 8 font stream sized to fit the viewport with a comfortable margin,
  • prints a tight 38-column panel with the failure detail, and
  • parks forever in a VSync(0) loop. The console must be reset to recover.

The on-screen panel includes:

  • Reason. A short string passed by the call site — e.g. "foregroundPilotRuntimeStart returned 0 (pack header / streaming buffer alloc failed)".
  • Scene. The slug that was loading (fishing1, walkstuf3, etc.).
  • At. The __FILE__:__LINE__ of the JC_BSOD call, with the directory prefix stripped so the line stays narrow.
  • Largest free block. Result of fgProbeLargestAlloc(), the existing binary-search heap probe. This is the single most useful number on the screen — it tells you whether the failure was a true heap-exhaust (small number) or something that wasn't an allocation problem at all (large number).
  • Likely causes. A short, deliberately generic list to give a non-developer something to type into a bug report.

Why not just a printf()?

The runtime also emits a JCBSOD block to TTY before it halts, with the same fields. That goes to the DuckStation console / regtest log so an external agent can pick the failure up automatically. But the on-screen BSOD is what makes the failure undeniable on a real TV, where there's no TTY console and no log file.

Two things drove that:

  1. The PS1 has no recoverable error path. There is no exception handler that can catch an out-of-memory and fall back to a degraded mode — once a scene's setup fails, the runtime is in a state we have to assume is corrupted. A loud visible halt is safer than papering over it.
  2. Silent fallback erases the diagnostic. If the engine quietly retries, or skips the broken scene, or tries to free something and continue, the heap state at the moment of failure is gone before you can ask about it. The BSOD freezes that state.

What to do when you see one

Two pieces of information matter most:

  • The scene slug on the BSOD. That tells you which pack we were trying to bring up.
  • The largest free block in KB. If this is small (say, < 100 KB) the failure is heap exhaustion: a preceding scene fragmented the heap, or some persistent allocation we made earlier in the session was bigger than it needed to be. If it's large (say, > 200 KB) and an allocation still failed, the failing alloc was simply asking for more than we have contiguous — likely a single big-frame pack like the fishing3 squid-emerge frame.

Photograph the screen, reset the console, and file the slug + KB number against the matching call site. The __FILE__:__LINE__ on the panel resolves to a single JC_BSOD() call in the source tree.

Testing the screen itself

Because the BSOD must never fire in production but must work the moment something subtle goes wrong, there's a BOOTMODE token that synthesizes a fatal failure on demand:

fgpilot bsod-test

With that flag set in config/ps1/BOOTMODE.TXT, the engine plays its first scene and then synthesizes a JC_BSOD() call right after. Used to verify the panel layout, font loading, and color rendering on real hardware vs. emulator without waiting for an organic failure.

Design notes

  • The 8 × 8 BIOS font is what the PSX BIOS provides via FntLoad. It is rendered through a separate FntOpen stream sized for the BSOD viewport, so the game's normal font usage isn't disturbed by anything still in flight when the failure hit.
  • Layout is 38 columns × ~21 lines. That fits comfortably inside 320 × 240 with margins, and gives enough horizontal space for typical reason strings without wrapping.
  • The blue is intentionally the Win 3.1 hue (~168 blue), not the Win 95+ hue. The 3.1 era had a less aggressive, slightly punctilious tone in its system-error voice — "A fatal error has occurred" rather than "Your PC ran into a problem" — and that voice is the one this port wants to borrow.
  • The on-screen text never references "press any key to continue" or "press a button to restart". There is no recovery path on the PS1; the only honest thing to print is "reset the console".

Hooks currently wired in

Two scene-setup failure paths in fgPlayOceanRuntimeScene now call JC_BSOD() instead of returning silently:

  • Pack-start failure — foregroundPilotRuntimeStart() returned 0. Caused by a metadata-prefix load failure, a non-base-diff pack flag, a sound-events load failure, or one of the per-scene streaming buffer mallocs failing.
  • Clean-rect setup failure — splits into two cases that previously shared a single message: (a) fgRuntimeComputeDrawBounds() couldn't compute a draw bbox (scene metadata missing or pack header malformed), or (b) fgBackdropSaveCleanBgRectsForPack() failed to allocate the rect-snapshot buffer (heap was too fragmented to hand out a contiguous chunk).

These were already early-returning on failure; the BSOD just makes the early-return loud. As more failure modes come up they get their own JC_BSOD() call sites with their own reason strings — the macro is cheap, and a one-line reason that points at a specific call site is worth more than ten lines of generic "an error occurred".
