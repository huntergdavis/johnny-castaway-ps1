# Holidays expansion pipeline

End-to-end documentation for the 4 → 35 holiday expansion in the Johnny
Castaway PS1 port. This is the operational doc — *how to use the
pipeline* — separate from the design ideation
(`holidays-expansion-design.md`), the locked plan
(`holidays-implementation-plan.md`), and the visual style contract
(`holidays-style-guide.md`).

## Phases

| Phase | What | Status |
|-------|------|--------|
| A | Per-holiday config + date-algorithm core (Meeus Easter, Nth-weekday math) | ✅ Shipped |
| B | AI-generated pixel art for the 31 new holidays + HTML preview | ✅ Generated, awaiting owner review |
| C | Owner reviews HTML, picks one variant per holiday (1=LITERAL, 2=MINIMALIST, 3=BUSY, 4=PLAYFUL) | ⏳ Awaiting owner |
| D | Pack chosen variants into HOLIDAY.PSB (or a sibling HOLIDAY2.PSB), update CD layout | ⏳ Post-review |
| E | Extend pause-menu Holiday cycling from 6 fixed states to 36 (AUTO + 35) | ⏳ Post-review |
| F | Headless DuckStation smoke-test forcing each holiday | ⏳ Post-review |

## Quick start

### Regenerate everything from scratch

```bash
cd /home/hunter/workspace/jc_ps1_sandbox

# 1. Regenerate the C holiday table from holidays.yml
python3 scripts/holidays-codegen.py
# → wrote src/holidays_table.c (35 holidays)
# → wrote scripts/holidays-art-spec.json (31 need art)

# 2. Smoke-test the date algorithms
python3 scripts/holidays-test.py
# → 20/20 should pass

# 3. Render all 31 × N variant PNGs (currently 4: LITERAL/MINIMALIST/BUSY/PLAYFUL)
python3 scripts/holidays-generate-art.py
# → Rendered: 124 (or 93 if v4 not yet authored)
# → Output dir: scratch/holidays-art/

# 4. Build the HTML review page
python3 scripts/holidays-preview.py
# → Wrote scratch/holidays-preview.html
xdg-open scratch/holidays-preview.html

# 5. Build the PS1 binary (links src/holidays.c into the runtime)
./scripts/build-ps1.sh
```

## The 16-color shared CLUT

Defined in `scripts/holidays_art_lib.py` as `PALETTE`:

| Idx | Name              | Hex      | Use                      |
|-----|-------------------|----------|--------------------------|
| 0   | transparent       | `#000000`| see-through              |
| 1   | white             | `#ffffff`| highlights, snow, paper  |
| 2   | black             | `#000000`| outlines, silhouettes    |
| 3   | skin (light)      | `#e0c090`| Johnny's face            |
| 4   | dark skin / trunk | `#a06e48`| palm trunk, shadows      |
| 5   | green             | `#388440`| palm fronds, grass       |
| 6   | dark green        | `#184820`| frond shadow             |
| 7   | sky / water       | `#4080e0`| daytime sky, ocean       |
| 8   | deep blue / night | `#102068`| night sky, lightsaber bg |
| 9   | sand / gold       | `#e4c878`| beach, parchment         |
| 10  | red / cardinal    | `#c83838`| flag, hearts, blood      |
| 11  | yellow            | `#f0c840`| sun, gold, lightning     |
| 12  | orange / pumpkin  | `#e07840`| pumpkin, sunset          |
| 13  | pink              | `#d890c0`| valentine, hibiscus      |
| 14  | purple            | `#a048a8`| mardi gras, twilight     |
| 15  | gray              | `#808080`| concrete, robots         |

All 35 sprites must use ONLY these 16 indices. Per-frame CLUTs are out
of scope for this iteration — every sprite shares the same palette.
This means some design-doc colors are approximated to the nearest CLUT
entry (e.g. "rhinestone collar pink" → `PINK`).

## Date-rule reference

`holidays.yml` `date_rule.kind` values:

```yaml
fixed:           { kind: fixed, month, day }
nth_weekday:     { kind: nth_weekday, n, weekday, month }
                 # n: 1..5 or -1 for last; weekday: 0=Sun..6=Sat
easter_offset:   { kind: easter_offset, offset }
                 # offset 0 = Easter Sunday; -47 = Mardi Gras
solstice:        { kind: solstice, month: 6 }      # summer
                 { kind: solstice, month: 12 }     # winter
equinox:         { kind: equinox, month: 3 }       # vernal
                 { kind: equinox, month: 9 }       # autumnal
election_day:    { kind: election_day }            # 1st Tue after 1st Mon Nov
```

The codegen normalizes the loose `equinox` / `solstice` kind into the
specific `equinox_vernal` / `equinox_autumnal` / `solstice_summer` /
`solstice_winter` C enum based on the month field.

## Variant convention

Every new holiday produces N variants (currently 3 + a planned 4th):

| Suffix | Style | Use case |
|--------|-------|----------|
| `v1` | LITERAL    | closest reading of the design doc concept |
| `v2` | MINIMALIST | stripped-down icon — 1-2 dominant elements |
| `v3` | BUSY/SCENIC| full island scene with palm + sand + Johnny |
| `v4` | PLAYFUL    | exaggerated/comedic — sweat drops, tilted, expressive |

Owner picks one variant per holiday from the HTML preview. The picks
JSON file becomes the input to Phase D (PSB packaging).

## How a sub-agent adds a new holiday

1. Add a row to `holidays.yml` with id, name, short_name, description,
   date_rule, sprite dimensions, palette hint, and `existing_sprite: null`.
2. Author render functions in the appropriate batch file (or create a new
   batch). Each function takes the holiday dict and returns a `Sprite`.
3. Update `RENDERERS_BATCHN = { id: (v1, v2, v3, v4) }`.
4. Run `python3 scripts/holidays-codegen.py` to regenerate
   `src/holidays_table.c` from the updated YAML.
5. Run `python3 scripts/holidays-generate-art.py` — new PNGs land in
   `scratch/holidays-art/`.
6. Run `python3 scripts/holidays-preview.py` — HTML reflects the new
   holiday automatically.
7. Run `./scripts/build-ps1.sh` to verify the C build still links.
8. Run `python3 scripts/holidays-test.py` to verify date-rule edge cases.

## Red-team checks already passing

Run as part of QA, all currently green:

1. **Dim/mode/presence** — all generated PNGs match spec dimensions, indexed mode, present on disk.
2. **Palette discipline** — only CLUT indices 0..15 used; no blanks; no pure-single-color sprites.
3. **Date logic over 7 years** — 35/35 holidays fire across 2024-2030 with 0 same-day collisions.
4. **Variant diversity** — every holiday's 3 variants are pixel-distinct.
5. **Cross-holiday duplicates** — no two holidays share artwork.
6. **Sparsity** — only 2 minimalist sprites use >85% single color (intentional negative-space designs).
7. **PS1 build clean** — `./scripts/build-ps1.sh` exits 0 with `holidays.c`/`holidays_table.c` linked.
8. **YAML schema sanity** — IDs 1..35 unique; short_names ≤12 chars; sizes within (32..160) × (32..96).
9. **HTML integrity** — 35 holiday cards, 93 embedded base64 PNGs, 93 radio buttons, sticky controls, save button.
10. **Cross-batch import sanity** — all 5 modules importable; expected function-count per file.

## Out of scope for this round

- **Per-frame CLUTs** — would let each holiday have its OWN 16-color palette
  instead of sharing. PSB format technically supports it; deferred.
- **Multi-frame animated sprites** — e.g. fireworks bursts, parade marching
  Johnny on Mardi Gras. Single static frame per holiday for now.
- **True Sierra-style hand-drawn pixel art** — current generation is procedural
  PIL primitives. Aim is RECOGNIZABLE not MASTERPIECE. Hand-iteration after
  owner review is the natural next step.
- **Holiday-specific island modifications** — the holiday sprite draws OVER
  the island, not BENEATH it. No changing the palm color, no sand-tint.
  The decoration sits beside the palm.
